# 从真实产品迭代里提炼的 UI 协作经验

envairrAN · 2026-09-24 · 公开版

这份总结提炼自真实产品协作中的截图、批注、要求与验收反馈。它不是对某个产品全部代码的审计，也不宣称记录了每一次最终修复的源码根因。公开版仅保留可复用方法。

## 你经常强调的九件事

| 你常说的话 | 真正要 AI 做的事 |
|---|---|
| “其他没有提到的部分不可以做任何改变” | 圈定组件、状态、样式及数据范围，控制 diff，不借局部任务重设计 |
| “先检查之后给我解决方案，不动手” | 先给证据、原因可信度和可评审方案，区分诊断与实施授权 |
| “优先检查/修改/删除/优化现有代码” | 找到真实维护入口，整理职责，不默认添 wrapper 或第二套实现 |
| “自查代码有无冲突、链接错误、CSS 累积” | 看实际生效的层叠规则、引用入口和线上产物，而不是只搜索源码 |
| “正文遵循‘收起’之前的间距，不能超出” | 把装饰效果与内容边界分开，以可见区域和操作区建立硬约束 |
| “底部路径不能低于完整展开的位置” | 验动画全过程的位置，不只验最终高度和终点截图 |
| “液态玻璃要渐隐，不能直接消失” | 明确淡出对象和退出生命周期，观察中间帧 |
| “不确定可以直观地追问我” | 用可看见的结果沟通差别，别让产品方先理解技术名词 |
| “保留指定版本作为回滚” | 确认发布与回滚产物，清理时保护依赖；不能擅自删除运行构建 |

还有两项贯穿很多细节：你希望可点击区域符合直觉，而非只点很小的文字；希望滚动、返回、交接都有连续性，尤其不能在最后一瞬间跳到位。

## 最有价值的转变：从评价变成约束

“动画不自然”很重要，它发现了问题；但 AI 仍可能只调速度。继续补上“卡片下边缘在收起的任意一帧，都不能低于完全展开时的位置”，就有了可以测量和否决的标准。

同样，“文字又漏出来了”可以落成：“正文只出现在‘收起’按钮上方的内容区，保留原定间距，渐变之外不得重新出现文字，展开、收起和滚动时都成立。”

公式不是让设计师承担工程工作。AI 应负责把你的直观描述翻译成几何、状态和职责，并用直观语言与你核对含义。

## 还原经验

先确认还原的是哪一稿、哪个状态、哪个视口；读取 Figma 的截图和结构，不只凭看起来相似。先修大比例、密度、字体与换行，再修材质。效果相似还不够，真实长文本、滚动、点击和动态过程也要符合。

Figma 中的布局是关系，不只是坐标。字号、行高、字体回退会影响整个卡片高度；一张图片上的模糊与透明，也需要在真实背景下检查。没有读到源数据的参数只能标为估计，不能假装精确。

使用已有组件、token 和资源能提高一致性；但不能照搬工具生成代码而绕开既有业务。设计文件出现某功能，不代表后端已经支持它。

## 品味不是风格开关

温柔、渐变、玻璃可以属于某个产品自己的表达。可推广的判断是：层级明确、比例协调、排版稳定、内容可读、材质有作用、反馈连续、交互符合用户预期。工具包不会规定“高级就要大留白/紫色/液态玻璃”。

还原和设计探索也不同：稿子已经确认时尊重稿；用户允许探索时，先理解用途，再做有理由的方向。小修不能变成 AI 的审美接管。

## 卡住时最重要的改变

同一个问题多次修不好，先换排查方法，而非再补一条样式。检查用户看到的是不是新版本；是不是改到了真正实例；样式究竟谁生效；状态是否被别的动画重置；滚动恢复是否在错误的时刻发生。

“优化现有代码”不是禁止合理封装，也不是删除所有覆盖，而是每一个层级和状态都能解释它的职责，失效代码能有依据地退出。

## 来源与边界

正文裁切、底边路径、材质渐隐、返回闪帧、整卡点击、滚动条例外来自真实迭代要求。Figma 经验参考设计工作记录，并核对了 [Figma 官方 MCP 文档](https://developers.figma.com/docs/figma-mcp-server/)。裁切语义核对 [MDN overflow](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/overflow)。具体历史修复的根因未逐一重审，案例不会把候选原因当事实。

旧记录中的导航、字体或画板尺寸不自动覆盖你后来的要求。共享包不包含聊天正文、服务器凭据、私有设计文件标识或业务数据。
