# 由真实参考组合界面

开始条件：产品方向、视觉风格、主题色、App/Web 已确认，或用户明确委托决定。缺项先按 [主动澄清](taste-and-clarification.md) 问清；不把已有示例风格当本次答案。

## 建立检索矩阵

将需求表转换为几组可检索关键词：

- 产品/人群：运动、学习、财务、旅行、创作与工作工具等，取自本轮需求。
- 页面/任务：记录、安排、查找、选择、比较、确认等。
- 组件/状态：timer、calendar、progress、player controls、filter、empty state 等。
- 已选平台/风格：iOS、web、minimal、soft gradient、editorial、professional 等。

产品任务线、组件线、视觉线可以来自不同品类。找不到「柔和渐变的运动产品」时，先找运动任务结构，再到专注/冥想/时间管理查计时组件，独立取得渐变参考。依 [跨品类组件检索](cross-domain-components.md) 保留目标输入输出和操作语义，不把风格与行业绑定。

只组合与本轮需求相符的词。逐项覆盖主要任务与关键组件，不无限扩搜、不过度采集。多个来源已能解释选型并覆盖关键状态即可结束；记录未覆盖的缺口。

## 来源选择与观察

优先用户指定来源及可用连接。Mobbin、Refero 可查页面与流程，Dribbble 可扩展组件和视觉概念，Godly 可补网站构图；这些是检索分工，作品证据类型仍需逐条确认。不可用时查公开产品官网、帮助中心、应用商店画面、官方设计系统和许可允许的 UI 库。先发现工具能力，不假装访问了付费或登录内容。重定向记录实际去向，不把搜索缓存当已打开的原站。

实际看图：记录 URL、日期、产品/平台、具体页面状态、可见组件。只有搜索摘要或文字说明就标“未做视觉核查”，不能写成已经看到。静态截图只能支持外观和层级判断，不能证明动画、滚动、错误恢复和真实后台能力。

不要求每次新建 UI 都重新阅读全套资料：已有符合本次需求、版本和状态的已核实参考可以复用，并说明来源。旧的 Mobbin 首页笔记仅是 [有限预览研究](mobbin-pattern-notes.md)，不能替代新的跑步/其他产品参考。

## 组件来源表

这是实现前的工作输入，不是完成后的补充包装。先为本轮主任务建立来源表，实际看对应画面，再编写相关组件。每个关键组件至少有一条已查看的具体证据；大站首页或“参考 Spotify”不足以覆盖生成版本选择、发布表单等不同任务。缺口按跨品类方法补查，不以泛泛“成熟模式”结束未完成检索。

记录组件在参考中的位置/裁图、输入与输出、可见状态，以及实现中的选择器/组件名。组合时保留实际观察到的信息层级、排列与操作关系，再统一主题色、PingFang、胶囊与图标。自己绘制一张唱片/背景，或只借封面色彩，不能代替产品组件参考。对齐前后保存并排证据，明确必要适配。

| 需求 ID / 页面 | 来源品类、URL与证据类型 | 采用的组件关系与状态 | 实现来源 | 需要统一/不能照搬 |
|---|---|---|---|---|
| 当前任务 | 具体屏幕/状态；产品屏/概念稿/策展预览 | 数字层级、控件排列、分组；结构和视觉来源可分列 | 现有代码 / 许可组件 / 按观察适配实现 | 字体、主题、密度、目标业务语义；品牌资产或未知行为 |

“沿用组件”有三个不同层次：

1. **代码复用**：项目已有组件、官方组件库或允许复用的开源源码；核对许可和依赖，优先现有栈。
2. **设计模式复用**：观察成熟产品里的组件结构、信息优先级和已知状态，适配需求重新实现；不要声称取得竞品源码。
3. **资产复用**：图标/图片/字体单独核对可用来源；公共可见不等于可随意打包。新增图标使用开源库 SVG，保留出处和许可证。

沿用有依据的结构，不能截图贴成整页冒充可交互 UI，也不能照搬不相关的品牌、虚假数据或未观察到的行为。关键组件缺参考时，先跨品类补查；仍有缺口可采用项目已有组件或成熟平台模式，明确哪些属于适配设计。只有需要改变核心业务语义或已确认方向时才追问，不因没有整屏竞品就停止工作。

可用风格不局限于最初提供的几个形容词；使用 [开放风格库](visual-style-library.md) 继续研究，但用户明确的极简等要求优先。

## 组合顺序

1. 确定统一的构图与视觉体系，组件结构可来自多个品类，并记录各自依据。按信息架构放置组件，不从不同 App 任意拼凑相反的密度、导航语义与操作习惯；不要求找到唯一能覆盖整屏的竞品。
2. 先验主要任务和状态：能看到什么、做什么、下一步在哪里。主次操作清楚，首屏不被装饰性数据或横幅占据。
3. 统一语义 token：字体角色、间距、文字层级、表面、边界、按钮尺寸与图标系列；保留组件适合其任务的形态。
4. 最后应用用户主题色到品牌、主要操作和选中态；对每种实际表面指定并测量其黑/白文字，按 [材质与对比](materials-and-contrast.md) 细化层次。错误/警告/成功保持语义；正文按明度保持清晰，不全部染成主题色。
5. 同一内容与视口下对照参考，逐项检查哪些关系被保留、哪些为需求做了必要改动。若改变了已确认的方向，先说明具体冲突并问用户。

## 交付与验证

实际产物应同时能回答：组件为什么存在、参考在哪里、操作是否可用。保存当前页面截图与组件来源表，避免只给“像 Apple”“更专业”之类评价。需要用户选择的方向可以做同内容的小对照，但不默认制作固定数量方案、不反复要求确认已决定的选项。

按 [视觉实现](modern-product-ui.md) 执行已选风格与会话约定；按 [验收](verification.md) 检查行为。有 Figma 时以指定稿为主要证据，并保留原有 [高还原诊断](fidelity-diagnostics.md)，不把拼组件工作流用来改写已经确认的设计。
