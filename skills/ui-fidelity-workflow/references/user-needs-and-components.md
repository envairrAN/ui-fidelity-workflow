# 从用户任务确定组件

## 先问问题是什么，不先挑控件

先检查已有要求，写一句 `谁在什么情境下，需要完成什么，以得到什么结果`。例如“跑步中快速判断是否需要调整速度”与“跑后比较本月进步”都与配速有关，但需要不同的信息顺序和操作密度。例子是设计推理，不是用户研究结果。

Google PAIR 的 [User Needs + Defining Success](https://pair.withgoogle.com/chapter/user-needs/) 强调先识别真实问题、理解现有做法，再判断 AI 是否有独特价值；自动化或辅助应符合用户想保留的控制，并用用户收益定义成功。本 skill 把这些原则转成下面的需求记录与组件映射，不要求普通 UI 项目建设 AI 系统。

## 最小需求记录

| 字段 | 记录方式 |
|---|---|
| 已确认 | 用户明确说过什么；记录来源或当前回答 |
| 当前行为 | 有什么真实观察/现有流程；没有就标未知 |
| 目标结果 | 完成任务后用户能做什么，不用“体验更高级”代替 |
| 场景约束 | 设备、环境、信息可得性、关键状态；只记录影响当前方案的项 |
| 待确认 | 存在不同产品含义的选择；写成具体问题 |
| 假设 | 仅供草案的可逆推断，不伪装成用户共同需求 |

产品方对范围的明确选择可以作为实现依据；它不自动等于已通过终端用户研究。没有真实参与者资料时，不生成虚构引语、百分比、画像和访谈样本。

## 提问应推进决策

- 不明确目标：询问一次真实使用情境或最重要任务，而不是“你需要哪些功能”。
- 多个目标：确认是否分别对应页面/Tab，或存在优先级；用户说全部要时明确纳入，不强迫只留一个。
- 功能词含混：例如“训练”，确认是查看计划、调整安排还是实时指导；不自行追加智能教练。
- 有既有流程：先读已有证据，只问仍影响实现的空白。
- 用户还没决定：给少量具体选项和权衡，等待答案；不要以“通常大家都这样”替代确认。

先问本轮关键缺口，一次 1–3 个问题。其他已明确的研究与文件整理继续；不对等待中的关键选择擅自实施。与视觉四项确认合并，避免两套问卷。

## 组件契约

按主要需求建一张小表，不要求每个像素都写文档：

| 需求/依据 | 页面与触发情境 | 数据/动作 | 组件与关键状态 | 成功条件 |
|---|---|---|---|---|
| 用户明确要求记录一次活动 | 记录页，准备开始 | 开始、暂停、继续、结束 | 主操作、计时信息、暂停态、结束确认 | 能完整完成流程且状态一致 |
| 用户明确要求查看计划 | 计划页，选某日 | 日期、任务、完成状态 | 日期切换、任务列表、空态 | 日期与任务同步，完成反馈清楚 |

这些是方法示例，不自动加入每个跑步项目。具体组件形式由后续参考决定，表里先写职责。不能以“竞品有”作为需求证据，竞品只证明某种实现模式存在。

检查每个主要组件：它服务什么任务？数据从哪里来？用户能做什么？没有数据时怎样？删除它是否影响任务？没有答案且只是填空的装饰不进入首稿。

## 页面与实现边界

先确定页面入口、主要内容、主操作、次操作、成功后的下一步。区分初始空态、已使用状态和操作中状态，不把三种状态混成一个漂亮截图。

数据区分真实、用户输入、计算、样本、未知；未知不显示为零。样本来源和开发限制记录在交付文档，不伪装真实定位、心率、训练推荐或社交活动。必要的产品能力边界仍要在发生操作时清楚表达。

产品确需 AI 时，另外确定输入、输出、用户可修改/拒绝的范围与失败后的替代路径。PAIR 的 [Mental Models](https://pair.withgoogle.com/chapter/mental-models/) 建议以用户收益说明能力；[Feedback + Control](https://pair.withgoogle.com/chapter/feedback-controls/) 讨论反馈含义与控制；[Errors + Graceful Failure](https://pair.withgoogle.com/chapter/errors-failing/) 要求出错后仍有前进路径。普通计时、导航、表单不因此改成 AI 功能。

## 采用的方法边界

研究方法与证据分级参考 GitHub `product-research`；页面任务、导航与状态组织参考 `website-studio`。已做取舍，见 [来源与采用](adopted-methods.md)。不要启动未请求的访谈、研究脚本或采样流程，不用软件格式检查证明需求已被用户验证。
